# MASTERHRMS — TWO-FACTOR AUTHENTICATION (TOTP) SECURITY AUDIT

## 1. Executive Summary

This audit report documents the architecture, cryptographic implementation, and security controls of the **Two-Factor Authentication (2FA)** subsystem in **MASTERHRMS**.

The platform implements RFC 6238 compliant **Time-based One-Time Passwords (TOTP)**, supporting standard authenticator applications (Google Authenticator, Microsoft Authenticator, 1Password, Apple Passwords). The implementation features authenticated symmetric encryption (AES-256-GCM) of stored secrets, cryptographically hashed single-use backup recovery codes, anti-replay caching, brute-force lockout protection, and official **MasterHRMS** issuer branding.

---

## 2. Architecture & Cryptographic Implementation

### 2.1 TOTP Secret Generation & Issuer Branding (`MFA-001`, `MFA-004`)
During 2FA setup initiation (`POST /api/auth/2fa/totp/initiate`):
1. A 20-byte base32 encoded secret is generated via `speakeasy.generateSecret`.
2. A standards-compliant `otpauth://` URI is constructed using `speakeasy.otpauthURL`:
   ```
   otpauth://totp/MasterHRMS (user@company.com)?secret=...&issuer=MasterHRMS&algorithm=SHA1&digits=6&period=30
   ```
3. **Issuer Branding Verification**:
   The URI strictly specifies `issuer=MasterHRMS`. When imported into mobile authenticator applications, the account is labeled with the official organization name **MasterHRMS**.
4. An SVG/PNG QR Code Data URL is generated from this URI and rendered to the user within the modal dialog alongside manual copy-paste backup secret strings.

### 2.2 AES-256-GCM Secret Encryption at Rest
Raw base32 secrets are NEVER stored in plaintext in the database:
- **Cipher**: AES-256-GCM (Galois/Counter Mode) providing confidentiality and cryptographic authenticity.
- **Key Derivation**: 256-bit encryption key derived from platform master secrets.
- **Serialized Format**: `iv:authTag:ciphertext`
- **Validation**: Any tampering or bit-flipping in the stored secret string causes decryption failure and authentication rejection.

### 2.3 Single-Use Backup Recovery Codes (`MFA-003`)
During enrollment, 8 high-entropy random backup codes are generated:
- **Format**: `XXXX-XXXX` (alphanumeric uppercase, e.g., `A1B2-C3D4`).
- **Storage Hashing**: Codes are normalized and hashed via SHA-256:
  ```typescript
  export function hashBackupCode(rawCode: string): string {
    const normalized = rawCode.trim().toUpperCase().replace(/[^A-Z0-9]/g, "");
    return crypto.createHash("sha256").update(normalized).digest("hex");
  }
  ```
- **Atomic Single-Use Consumption**: When a backup code is verified during authentication:
  - The submitted hash is located within the user's stored backup code array.
  - The matched hash is atomically removed from the array (`splice`) and the updated array persisted.
  - Re-submission of the identical backup code fails immediately with HTTP 400.

## 3. Verification & Anti-Replay Protections (`MFA-002`)

### 3.1 Setup Confirmation (`POST /api/auth/2fa/totp/confirm`)
To prevent lockouts due to misconfigured authenticator apps:
1. `twoFactorEnabled` remains `false` during secret generation.
2. The user must submit a valid 6-digit TOTP token generated by their newly configured app.
3. The server decrypts the stored secret and validates the code with a window tolerance of $\pm 30$ seconds (window size 1).
4. Only upon successful verification is `twoFactorEnabled` set to `true` and `twoFactorConfirmedAt` recorded.
5. An audit mutation event and branded security email are published.

### 3.2 Anti-Replay Cache
To eliminate token replay within the 30-second window:
- Successful TOTP tokens are recorded in an in-memory cache keyed by `${userId}:${token}` with a 90-second expiration.
- If the identical code is submitted again within its validity window, it is rejected: `"Code has already been used. Please wait for the next TOTP code."`

### 3.3 Rate Limiting & Brute-Force Lockout
To prevent automated code enumeration:
- Failed verification attempts are tracked in memory per user.
- **Max Failures**: 5 consecutive failed attempts.
- **Lockout Duration**: 15 minutes (`LOCKOUT_MS = 15 * 60 * 1000`).
- While locked out, verification requests immediately return HTTP 429 / 400 with the exact remaining lockout seconds.
