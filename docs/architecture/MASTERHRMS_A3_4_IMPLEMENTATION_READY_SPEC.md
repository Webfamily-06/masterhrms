## 1. Executive Summary & Architectural Scope

Phase A3.4 defines the architecture for transforming an immutable, paid commerce order (`CommerceOrder` with `status = 'PAID'`) into active tenant capabilities without double-provisioning, partial failure, cross-tenant pollution, or silent data corruption.

```
┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│                                PHASE A3.3 BOUNDARY (CLOSED)                                 │
│  [Checkout Complete] ──► [CommerceOrder: PAID, fulfillmentStatus: UNFULFILLED]              │
└──────────────────────────────────────────────┬──────────────────────────────────────────────┘
                                               │
                                               ▼
┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│                                   PHASE A3.4 PIPELINE                                       │
│                                                                                             │
│  1. Transactional Outbox Intent:                                                            │
│     COMMERCE_ORDER_PAID event persisted in `outbox_events` atomically with order settlement.│
│                                                                                             │
│  2. Asynchronous Fulfillment Consumer:                                                      │
│     - Claims order via PostgreSQL row-lock (`FOR UPDATE SKIP LOCKED`).                      │
│     - Resolves canonical entitlement mapping from `priceSnapshot.items`.                    │
│                                                                                             │
│  3. Atomic Provisioning Transaction (`db.$transaction`):                                    │
│     ├── Update `commerce_orders.fulfillment_status = 'FULFILLED'` (optimistic lock)         │
│     ├── Upsert `TenantSubscription` (if Base Plan)                                          │
│     ├── Upsert `TenantModule` (if Standalone ERP Product: POS, CRM, Finance)                │
│     ├── Upsert `TenantAddon` (if Add-On: Biometrics, Google Workspace, etc.)                │
│     ├── Record `AuditLog` entry (COMMERCE_FULFILLMENT_SUCCEEDED)                            │
│     └── Mark `outbox_events.status = 'PROCESSED'`                                           │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
```

## 2. Requirement A: Paid Order to Entitlement Mapping

### 2.1 Authoritative Item Resolution
Entitlements are derived **exclusively** from the immutable `order.priceSnapshot.items` array generated by the authoritative pricing engine in Phase A3.2. Client-supplied metadata or post-order catalog modifications are strictly ignored.

Each line item in `priceSnapshot.items` is resolved against the `CANONICAL_CATALOG_REGISTRY` in `server/src/services/unified-catalog.service.ts`:

| Catalog Product ID | Item Slug | Product Type | Target Engine | Target Table & Mutation |
| :--- | :--- | :--- | :--- | :--- |
| `plan_starter` | `starter` | `BASE_PLAN` | `subscription` | `TenantSubscription`: `planId = 'plan_starter'`, `status = 'active'`, `maxEmployees = 25`, `billingInterval = item.billingInterval` |
| `plan_growth` | `growth` | `BASE_PLAN` | `subscription` | `TenantSubscription`: `planId = 'plan_growth'`, `status = 'active'`, `maxEmployees = 100`, `billingInterval = item.billingInterval` |
| `plan_sovereign` | `sovereign` | `BASE_PLAN` | `subscription` | `TenantSubscription`: `planId = 'plan_sovereign'`, `status = 'active'`, `maxEmployees = 500`, `billingInterval = item.billingInterval` |
| `plan_custom_flex` | `custom-flex` | `BASE_PLAN` | `subscription` | `TenantSubscription`: `planId = 'plan_custom_flex'`, `status = 'active'`, `maxEmployees = item.seats`, `pricePerUser = item.unitPrice` |
| `prod_pos` | `pos` | `STANDALONE_PRODUCT` | `module` | `TenantModule`: `moduleKey = 'product_pos'`, `isEnabled = true` |
| `prod_crm` | `crm` | `STANDALONE_PRODUCT` | `module` | `TenantModule`: `moduleKey = 'product_crm'`, `isEnabled = true` |
| `prod_finance` | `finance` | `STANDALONE_PRODUCT` | `module` | `TenantModule`: `moduleKey = 'product_finance'`, `isEnabled = true` |
| `addon_biometric_sync` | `biometric-sync` | `ADDON_FEATURE` | `addon` | `TenantAddon`: `addonSlug = 'biometric-sync'`, `status = 'active'`, `plan = 'standard'` |
| `addon_google_workspace` | `google-workspace` | `ADDON_INTEGRATION` | `addon` | `TenantAddon`: `addonSlug = 'google-workspace'`, `status = 'active'`, `plan = 'standard'` |
| `addon_asset_management` | `asset-management` | `ADDON_FEATURE` | `addon` | `TenantAddon`: `addonSlug = 'asset-management'`, `status = 'active'`, `plan = 'standard'` |

### 2.2 Multi-Product Independence (No Forced HRMS Coupling)
- A purchase of `prod_pos` or `prod_crm` **does NOT require** an HRMS base subscription.
- Standalone products provision `TenantModule` directly, enabling the tenant workspace to access the standalone portal (`/pos`, `/crm`, `/finance`) independently of HRMS subscription status.

### 2.3 Subscription Period Calculation
For `targetEngine === "subscription"`:
- **Monthly (`1_month`):**
  - `currentPeriodStart = paidAt`
  - `currentPeriodEnd = paidAt + 1 calendar month` (calculated using deterministic UTC day-preservation with end-of-month clamp).
- **Annual (`1_year`):**
  - `currentPeriodStart = paidAt`
  - `currentPeriodEnd = paidAt + 1 calendar year`.

### 2.4 Existing Entitlement Conflict & Upgrade Rules
- **Base Plan Upgrade:** If the tenant already has an active `TenantSubscription`, purchasing a higher tier (e.g. `growth` when on `starter`):
  1. Updates `planId = 'plan_growth'`.
  2. Updates `maxEmployees = 100`.
  3. Resets `currentPeriodStart = paidAt` and calculates new `currentPeriodEnd`.
  4. Records `SubscriptionPolicyAudit` event `UPGRADE`.
- **Standalone Module Repeat Purchase:** If `TenantModule` already exists with `isEnabled = true`, fulfillment is an idempotent no-op (preserves enabled state).
- **Add-on Renewal:** If `TenantAddon` is already active, fulfillment extends `renewsAt` by the purchased duration.

### 2.5 Order Eligibility Guard
An order is eligible for fulfillment **if and only if**:
1. `order.status === 'PAID'` (Strict check; any `DRAFT`, `PENDING_PAYMENT`, `FAILED`, `CANCELLED`, or `EXPIRED` order is immediately rejected).
2. `order.fulfillmentStatus === 'UNFULFILLED'` (Prevents duplicate processing).
3. `order.priceSnapshot.items` is non-empty and syntactically valid.

## 3. Requirement B: Atomicity & Idempotent Fulfillment

### 3.1 Worker Concurrency & Claiming Protocol
To guarantee that two concurrent fulfillment workers never process the same order simultaneously, workers must claim the order using an atomic conditional update:

```sql
UPDATE commerce_orders
SET fulfillment_status = 'CLAIMED',
    version = version + 1,
    updated_at = statement_timestamp()
WHERE id = :orderId
  AND tenant_id = :tenantId
  AND status = 'PAID'
  AND fulfillment_status = 'UNFULFILLED'
  AND version = :expectedVersion;
```

**Outcome Handling:**
- **Rows affected == 1:** Worker has acquired exclusive execution rights.
- **Rows affected == 0:** Order is already claimed, fulfilled, or modified. Worker aborts cleanly with zero mutations.

### 3.2 The Atomic Provisioning Transaction
Once claimed, all provisioning actions are executed within a single interactive PostgreSQL transaction (`prisma.$transaction`):

```typescript
await db.$transaction(async (tx) => {
  // 1. Re-verify order lock inside transaction
  const order = await tx.commerceOrder.findUnique({
    where: { id: orderId },
    select: { id: true, tenantId: true, status: true, fulfillmentStatus: true, priceSnapshot: true, version: true }
  });

  if (!order || order.status !== "PAID" || order.fulfillmentStatus !== "CLAIMED") {
    throw new Error("ORDER_INELIGIBLE_FOR_FULFILLMENT");
  }

  // 2. Iterate through items and provision targets
  for (const item of order.priceSnapshot.items) {
    if (item.targetEngine === "subscription") {
      await tx.tenantSubscription.upsert({
        where: { tenantId: order.tenantId },
        create: {
          tenantId: order.tenantId,
          planId: item.productId,
          status: "active",
          billingInterval: item.billingInterval,
          currentPeriodStart: paidAt,
          currentPeriodEnd: calculatePeriodEnd(paidAt, item.billingInterval),
          maxEmployees: item.includedSeats || 25,
        },
        update: {
          planId: item.productId,
          status: "active",
          billingInterval: item.billingInterval,
          currentPeriodStart: paidAt,
          currentPeriodEnd: calculatePeriodEnd(paidAt, item.billingInterval),
          maxEmployees: item.includedSeats || 25,
        }
      });
    } else if (item.targetEngine === "module") {
      await tx.tenantModule.upsert({
        where: {
          tenantId_moduleKey: {
            tenantId: order.tenantId,
            moduleKey: item.entitlementKey,
          }
        },
        create: {
          tenantId: order.tenantId,
          moduleKey: item.entitlementKey,
          isEnabled: true,
        },
        update: {
          isEnabled: true,
        }
      });
    } else if (item.targetEngine === "addon") {
      await tx.tenantAddon.upsert({
        where: {
          tenantId_addonSlug: {
            tenantId: order.tenantId,
            addonSlug: item.slug,
          }
        },
        create: {
          tenantId: order.tenantId,
          addonSlug: item.slug,
          status: "active",
          plan: "standard",
          renewsAt: calculatePeriodEnd(paidAt, item.billingInterval || "1_month"),
        },
        update: {
          status: "active",
          renewsAt: calculatePeriodEnd(paidAt, item.billingInterval || "1_month"),
        }
      });
    }
  }

  // 3. Mark Order as FULFILLED
  await tx.commerceOrder.update({
    where: { id: order.id },
    data: {
      fulfillmentStatus: "FULFILLED",
      fulfilledAt: new Date(),
      version: { increment: 1 },
    }
  });

  // 4. Mark Outbox Event as PROCESSED
  await tx.outboxEvent.updateMany({
    where: {
      entityType: "CommerceOrder",
      entityId: order.id,
      eventType: "COMMERCE_ORDER_PAID",
      status: "PENDING",
    },
    data: {
      status: "PROCESSED",
      processedAt: new Date(),
    }
  });

  // 5. Append AuditLog Entry
  await tx.auditLog.create({
    data: {
      tenantId: order.tenantId,
      actorId: "SYSTEM_FULFILLMENT_ENGINE",
      action: "COMMERCE_FULFILLMENT_SUCCEEDED",
      entityType: "CommerceOrder",
      entityId: order.id,
      afterJson: { itemsProvisioned: order.priceSnapshot.items.length },
    }
  });
});
```

## 4. Requirement C: Transactional Outbox & Event Architecture

### 4.1 Native Outbox Grounding
The repository already contains `model OutboxEvent` (`outbox_events` in PostgreSQL) with:
- `id` (UUID PK)
- `tenantId` (FK to `tenants(id)`)
- `eventId` (Unique identifier)
- `eventType` (`VARCHAR(100)`)
- `entityType` (`VARCHAR(100)`)
- `entityId` (`VARCHAR(64)`)
- `payload` (`JSONB`)
- `status` (`PENDING`, `PROCESSED`, `FAILED`)
- `retryCount` (`INT`, default 0)
- `error` (`TEXT`)
- `occurredAt`, `processedAt`, `createdAt`
- Index on `(tenantId, status, occurredAt)`
- Index on `(status, retryCount)`

### 4.2 Publication at Payment Commit
When an order transitions to `PAID` (during live webhook processing or simulation), the payment transaction creates the outbox record **in the same transaction**:

```typescript
await tx.outboxEvent.create({
  data: {
    tenantId: order.tenantId,
    eventId: crypto.randomUUID(),
    eventType: "COMMERCE_ORDER_PAID",
    entityType: "CommerceOrder",
    entityId: order.id,
    actorId: actorId || "SYSTEM",
    status: "PENDING",
    payload: {
      orderId: order.id,
      orderNumber: order.orderNumber,
      tenantId: order.tenantId,
      amountInPaise: order.amountInPaise,
      currency: order.currency,
      items: order.priceSnapshot.items,
      paidAt: order.paidAt,
    }
  }
});
```

### 4.3 Multi-Worker Safe Event Claiming
To support multi-instance horizontal scaling, the background outbox consumer sweeps pending events using PostgreSQL `SKIP LOCKED`:

```sql
SELECT id, event_id, tenant_id, payload, retry_count
FROM outbox_events
WHERE status = 'PENDING'
  AND retry_count < 5
ORDER BY occurred_at ASC
LIMIT 10
FOR UPDATE SKIP LOCKED;
```

### 4.4 Worker Heartbeat and Lease Expiration
If a worker crashes after claiming an order (`fulfillment_status = 'CLAIMED'`) but before the transaction commits:
- A sweep query runs every 5 minutes checking for orders in `CLAIMED` state where `updated_at < NOW() - INTERVAL '5 minutes'`.
- These orphaned claims are reset to `UNFULFILLED`, enabling other workers to process them.

## 5. Requirement D: Audit and Observability

### 5.1 Standardized Audit Events
All fulfillment events are emitted using `AuditService.logMutation()` to the `audit_logs` table:

| Action | Entity Type | Actor | Metadata Payload |
| :--- | :--- | :--- | :--- |
| `COMMERCE_FULFILLMENT_REQUESTED` | `CommerceOrder` | `SYSTEM` | `{ orderId, orderNumber, itemCount }` |
| `COMMERCE_FULFILLMENT_CLAIMED` | `CommerceOrder` | `WORKER_ID` | `{ workerInstance, leaseExpiresAt }` |
| `COMMERCE_FULFILLMENT_SUCCEEDED` | `CommerceOrder` | `SYSTEM` | `{ durationMs, provisionedTargets }` |
| `COMMERCE_FULFILLMENT_RETRY_SCHEDULED` | `CommerceOrder` | `SYSTEM` | `{ attempt, nextRetryAt, error }` |
| `COMMERCE_FULFILLMENT_FAILED_PERMANENT` | `CommerceOrder` | `SYSTEM` | `{ finalError, requiresManualIntervention: true }` |
| `COMMERCE_ENTITLEMENT_CONFLICT` | `CommerceOrder` | `SYSTEM` | `{ conflictType: "ACTIVE_PLAN_OVERWRITE", oldPlan, newPlan }` |

### 5.2 Privacy & Masking Invariants
- Zero credit card numbers, payment gateway tokens, or bank account credentials may be recorded in `payload`, `metadata`, or `AuditLog.afterJson`.
- All logs are strictly tagged with `tenant_id` to prevent cross-tenant log pollution.

## 6. Requirement E: Standalone Product Invoicing (OD-3 Analysis)

### 6.1 The Engineering Dilemma
In `server/prisma/schema.prisma`, `BillingInvoice` is defined with:
```prisma
model BillingInvoice {
  id             String             @id @default(uuid()) @db.VarChar(36)
  tenantId       String             @map("tenant_id") @db.VarChar(36)
  subscriptionId String             @map("subscription_id") @db.VarChar(36)
  subscription   TenantSubscription @relation(fields: [subscriptionId], references: [id], onDelete: Cascade)
  ...
}
```
Because `subscriptionId` is **NOT NULL**, standalone purchases (POS, CRM, Finance) cannot create a `BillingInvoice` without either:
1. Creating a dummy/empty subscription, OR
2. Changing the schema.

### 6.2 Comparison of Architectural Options

| Dimension | Option A: Make `BillingInvoice.subscriptionId` Nullable | Option B: Dedicated `CommerceReceipt` Ledger |
| :--- | :--- | :--- |
| **Schema Impact** | Requires additive migration `ALTER TABLE billing_invoices ALTER COLUMN subscription_id DROP NOT NULL`. | Requires new model `CommerceReceipt` and new table `commerce_receipts`. |
| **Referential Integrity** | `subscriptionId` becomes optional foreign key (`onDelete: SetNull`). | Preserves strict foreign key on `BillingInvoice`; `CommerceReceipt` links directly to `CommerceOrder`. |
| **Existing Code Risk** | Medium: Queries assuming `invoice.subscription` is always present must be audited and guarded with null checks. | Zero: `BillingInvoice` queries remain 100% untouched and backward-compatible. |
| **GST Invoice Numbering** | Unified sequential tax invoice series across all SaaS purchases (`INV-YYYY-XXXXX`). | Two distinct numbering sequences (`SUB-INV-XXXX` vs `COM-REC-XXXX`), requiring tax register consolidation. |
| **Reporting Complexity** | Low: Single table query for tenant spend, accountant P&L exports, and GST GSTR-1 filings. | High: Queries compiling annual revenue must perform `UNION ALL` across both invoice tables. |
| **Operational Recommendation** | **Recommended for long-term SaaS architecture** (unified financial ledger). | Recommended only if strict separation between recurring billing and one-off store sales is legally mandated. |

**Owner Action Required:** The Owner must formally decide between Option A and Option B before A3.4 implementation.

## 7. Requirement F: Commercial & Live Gateway Dependencies

### 7.1 Commercial Pricing Schedule (`OD-1`)
- Production prices for plans, seat bands, and add-ons remain **UNAPPROVED**.
- Phase A3.4 must maintain the fail-closed pricing engine from Phase A3.2 (`UNCONFIGURED_PRODUCT_PRICING`).
- No live commerce order may be processed until the Owner formally executes the `OD-1` approval schedule.

### 7.2 Future Live Payment Integration Architecture
When authorized, live gateway integration must follow these specifications:

```
┌─────────────────────────┐          ┌───────────────────────────────────┐
│ Gateway (Razorpay/Stripe│──POST───►│ POST /api/commerce/webhooks       │
└─────────────────────────┘          └─────────────────┬─────────────────┘
                                                       │
                                 1. Constant-Time HMAC Signature Check
                                 2. Replay Check (PaymentWebhookEvent)
                                 3. Amount & Currency Parity Check
                                                       │
                                                       ▼
                                     ┌───────────────────────────────────┐
                                     │ Update Order: status = 'PAID'     │
                                     │ Create OutboxEvent: PENDING       │
                                     └─────────────────┬─────────────────┘
                                                       │
                                                       ▼ (Decoupled Async)
                                     ┌───────────────────────────────────┐
                                     │ A3.4 Entitlement Fulfillment      │
                                     └───────────────────────────────────┘
```

1. **Webhook Signature Verification:**
   - **Razorpay:** `crypto.createHmac('sha256', secret).update(rawBody).digest('hex') === req.headers['x-razorpay-signature']` using `crypto.timingSafeEqual`.
   - **Stripe:** `stripe.webhooks.constructEvent(rawBody, signature, secret)` with timestamp drift tolerance $\le 300\text{s}$.
2. **Replay Protection:** Deduplication enforced by `PaymentWebhookEvent.deliveryKey` unique index. Duplicate webhook deliveries return HTTP 200 without re-fulfilling.
3. **Amount Parity Guard:** Gateway `amount` (in paise/cents) must strictly match `order.amountInPaise`. Any mismatch halts the order in `FLAGGED_MISMATCH` with zero fulfillment.

## 8. Failure and Recovery Matrix

| # | Failure Scenario | System State | Recovery Policy | Audit Event | Operator Action |
| :---: | :--- | :--- | :--- | :--- | :--- |
| **1** | Duplicate fulfillment request | Order already `FULFILLED` | No-op. Worker returns success without duplicate provisioning. | `COMMERCE_FULFILLMENT_DUPLICATE_IGNORED` | None. |
| **2** | Two workers claim same order | First worker updates to `CLAIMED` | Second worker receives 0 affected rows and aborts. | `COMMERCE_FULFILLMENT_CLAIM_COLLISION` | None. |
| **3** | Worker crash during transaction | DB transaction rolls back | Order remains in `CLAIMED`. Lease expires after 5m and resets to `UNFULFILLED`. | `COMMERCE_FULFILLMENT_LEASE_EXPIRED` | Automatic retry on next sweep. |
| **4** | Missing or retired catalog slug | Item cannot be resolved | Transaction rolls back. Order marked `FAILED` with reason `UNKNOWN_CATALOG_PRODUCT`. | `COMMERCE_FULFILLMENT_FAILED_PERMANENT` | Operator investigates catalog mapping. Manual retry required. |
| **5** | Conflicting active subscription | Tenant already on higher tier | Evaluates plan hierarchy. Upgrades tier or extends duration. Does not corrupt state. | `COMMERCE_ENTITLEMENT_CONFLICT_RESOLVED` | None. |
| **6** | Database connection timeout | Transaction aborted | Exponential backoff retry scheduled. | `COMMERCE_FULFILLMENT_RETRY_SCHEDULED` | Automated retry. |
| **7** | Max retries (5) exceeded | Event marked `FAILED` in outbox | Halts automated retries. Order flagged for manual intervention. | `COMMERCE_FULFILLMENT_ESCALATED` | Operator alerted via dashboard. |
| **8** | Unverified payment evidence | Order status is not `PAID` | Fulfillment immediately rejected with `403 ORDER_NOT_PAID`. | `COMMERCE_ORDER_INELIGIBLE_REJECTED` | Security audit if repeated. |
| **9** | Webhook arrives for deleted tenant | Tenant ID not found in DB | Fulfillment fails closed. Order flagged orphaned. | `COMMERCE_FULFILLMENT_ORPHANED_TENANT` | Manual compliance review. |
| **10**| Customer payment refunded | Order marked `REVERSED` | Authoritative revocation pipeline disables `TenantModule` / cancels `TenantSubscription`. | `COMMERCE_ENTITLEMENT_REVOKED` | Automated reversal. |
