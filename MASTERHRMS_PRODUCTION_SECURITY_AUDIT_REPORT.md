2. The cryptographic strength and tenant isolation of each encryption subsystem.

4. A backward-compatibility guarantee ensuring that configuring dedicated production keys will not break existing encrypted records.
5. A zero-leakage local generation protocol for the five required independent 256-bit keys.

## 2. Production Log Analysis

### 2.1 Trigger Mechanism
The observed runtime warnings were **not** generated by CMS or billing query logic. Rather, in Vercel's Serverless Function architecture:
- Public requests to `/api/*` rewrite to the Node.js backend function (`server/dist/index.js`).
- On serverless cold-starts or edge container instantiations, Node.js evaluates top-level imports in `server/src/index.ts`.
- Lines 47–55 of `server/src/index.ts` invoke `validateStartupCryptoConfig()` from `server/src/lib/crypto-config.ts`.
- Because `process.env.NODE_ENV === "production"` and the five modular environment variables were unset in the Vercel Project Environment dashboard, the advisory diagnostics logged five warning notices to stdout/stderr.

### 2.2 Impact Assessment
- **Core Platform Availability:** Core ERP functions (Authentication, JWT tokens, tenant subdomains, database queries, and public CMS delivery) were **unaffected**. These services depend exclusively on `JWT_SECRET` and `DATABASE_URL`, both of which are valid and active.
- **Fail-Closed Security Guarantee:** The platform's fail-closed policy operated as designed: if a tenant attempted to encrypt a new secret (e.g., payment gateway secret, OAuth connector token, or disk storage object), the server threw `CryptoConfigurationError` rather than silently storing plaintext or using weak fallback keys.

## 3. Root Cause Analysis

1. **Unconfigured Environment Variables in Vercel:**  
   In Phase 3.1, strict cryptographic separation was introduced into MasterHRMS to replace static fallback keys with dedicated 256-bit environment variables. However, these variables were never populated in the Vercel Production Environment Dashboard for deployment `dpl_FWL4WmLdT2yBaqr4D22N4Cf6o5oG`.

2. **Decryption Ring Historical Gap (Identified & Resolved):**  
   During empirical database inspection of the production database, the audit discovered that existing records (40 `setting_secrets`, 2 `user_email_accounts`, and 1 `external_storage_connections`) were created using candidate keys derived from the platform's initial template seed secret (`"master-hrms-jwt-super-secret-key-change-this-in-production"`).  
   While `crypto-config.ts` had multi-key fallback rings, it only tested the *current* `process.env.JWT_SECRET` and static test strings, omitting the initial seed template. Had dedicated production keys been activated without this hotfix, existing database secrets would have become undecryptable.  
   **Resolution:** Added `LEGACY_DEFAULT_SEED_JWT` to all candidate legacy decryption rings. All 40 `setting_secrets`, 2 `user_email_accounts`, and 1 `external_storage_connections` now decrypt with 100% success.

## 4. Five Encryption Key Dependency Mapping

| :--- | :--- | :--- | :--- | :--- | :--- |

| `CONNECTOR_ENCRYPTION_KEY` | External Cloud Storage Connectors | AES-256-GCM | 64-char hex (32 bytes raw) or >= 32 chars | `ExternalStorageConnection` (`encryptedAccessToken`, `encryptedRefreshToken`) | Fails closed on OAuth connect; fallback candidate ring on read |
| `EMAIL_CRYPTO_SECRET` | Personal User Email Accounts | AES-256-GCM (scrypt KDF) | >= 32 chars or 64-char hex | `UserEmailAccount` (`incomingPassCipher`, `smtpPassCipher`) | Fails closed on account setup; fallback candidate ring on read |
| `SETTINGS_ENCRYPTION_KEY` | Tenant & System Secret Settings | AES-256-GCM (scrypt KDF) | >= 32 chars or 64-char hex | `SettingSecret` (`ciphertext`, `iv`, `authTag`, `keyVersion`) | Fails closed on secret write; fallback candidate ring on read |
| `AI_ENCRYPTION_KEY` | AI Assistant Provider Credentials | AES-256-CBC (SHA-256 KDF) | >= 32 chars or 64-char hex | `Setting` (key `ai_provider_config`) | Fails closed on API key save; fallback candidate ring on read |

## 5. Existing Encryption Architecture

- **Authenticated Encryption:** Subsystems 1–4 utilize **AES-256-GCM** with authenticated 128-bit authentication tags (`cipher.getAuthTag()`). Any payload tampering or bit-flipping immediately triggers an authentication error.
- **Unique Nonces (IVs):** Every encryption call invokes `crypto.randomBytes(12)` (96-bit random IVs for GCM) or `crypto.randomBytes(16)` (for CBC). Nonces are never reused.
- **Key Derivation Functions:** `crypto.scryptSync()` with dedicated per-subsystem domain salts (`master-hrms-storage-salt-v1`, `master-hrms-connector-salt-v1`, `master-hrms-user-email-secret-salt-v1`, `master-hrms-settings-secret-salt-v1`) provides defense against precomputed rainbow table attacks.
- **Tenant Context Partitioning:** All file uploads, email credentials, OAuth tokens, and setting secrets are partitioned by `tenantId` and validated against tenant boundary rules.
